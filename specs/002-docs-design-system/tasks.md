# Tasks: Documentation Design System & Visual Redesign

**Input**: Design documents from `specs/002-docs-design-system/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/design-system.md, quickstart.md

**Tests**: No automated test tasks — this is a presentation-only feature. Validation is manual/visual + diff-based invariance checks (see quickstart.md V1–V8). No TDD was requested.

**Organization**: Tasks are grouped by user story (US1 P1 MVP, US2 P2, US3 P3) for independent implementation and testing.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: US1 / US2 / US3 (Setup, Foundational, Polish have no story label)
- All paths are repo-relative from `C:\git\drapo\docs`.

## Hard boundaries (apply to EVERY task)

- Do **not** edit documentation content: nothing under `src/WebDocs/wwwroot/app/menu/**`, `functions/*/description.html`, `functions/*/parameters.json`, or sample `content.html` (FR-002).
- Do **not** edit the MCP / serving layer: nothing under `src/WebDocs/Controllers`, `Services`, `Models`, or MCP wiring (FR-003).
- Do **not** hand-edit the build output `src/WebDocs/wwwroot/css/theme.css` (generated by Cake `less`).
- Shared-sector / component edits are **presentation only** — keep every `d-*` attribute, `d-sector`, `d-dataKey`, and event binding identical (research D7).

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: no dependencies — start immediately.
- **Foundational (Phase 2)**: depends on Setup — **BLOCKS all user stories** (everything consumes tokens).
- **User Stories (Phase 3–5)**: all depend on Foundational. US1 is the MVP; US2 formalizes/documents US1's look; US3 polishes both themes.
- **Polish (Phase 6)**: depends on the desired user stories being complete.

### User Story Dependencies

- **US1 (P1)**: after Foundational. No dependency on US2/US3. Independently shippable MVP.
- **US2 (P2)**: after Foundational. Systematizes US1's styling; best done after US1 so patterns reflect real usage, but its deliverables (pattern layer, docs, literal-sweep) are independently testable.
- **US3 (P3)**: after Foundational. Dark/light polish is testable on whatever surfaces exist; strongest after US1 surfaces are styled.

### Within Each Story

- Foundation tokens before any surface refactor.
- Feature stylesheet refactors (T009–T015) are parallel — different files.
- Shared-sector markup (T016) and component restyle (T017) after their stylesheets exist.
- Verification tasks (T018, T022–T023, T026–T027) after their implementation tasks.

### Parallel Opportunities

- Setup: T003, T004 in parallel.
- US1: T009–T015 all `[P]` (independent `.less` files) can run together; then T016, T017; then T018.
- US2: T019 and T021 `[P]`; T020 after T019; then T022, T023.
- US3: T025 `[P]` alongside the T024 audit; then T026, T027.
- Polish: T028–T031 all `[P]`; T032 last.

### Notes

- `[P]` = different files, no incomplete dependency.
- Commit after each task or logical group; keep commits presentation-scoped (mirror repo commit style).
- Re-run the Cake `less` build after any `styles/*.less` change; restart `dotnet run` only if verifying content pages.
- Never let a diff touch documented content or the serving layer — if it does, revert and re-scope.
